<Aside title="Running the CLI">
  Install Mantix in your project with `npm install --save-dev mantix`, `pnpm add
  --save-dev mantix` or `bun add --dev mantix`. Then run it as `npx mantix …`,
  `pnpm mantix …` or `bunx mantix …`. Inside a clone of the Mantix repository,
  `pnpm mantix …` runs the CLI straight from its TypeScript source. Commands and
  flags may still change before version 1.0.
</Aside>

## mantix run

Runs a test file headless, prints progress and a summary, checks thresholds,
and exits with a code your CI can act on.

```sh
mantix run <file> [--rate N] [--vus N] [--duration 30s] [--repeat N] [--base-url URL] [--json out.json] [--quiet] [--label "text"] [--no-history]
```

| Flag              | What it does                                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<file>`          | The test file. Its default export is one scenario or an array of them.                                                                                            |
| `--rate N`        | Replace every scenario's load with a constant rate of `N` iterations per second (open model). A `maxVus` from the file is kept.                                   |
| `--vus N`         | Replace every scenario's load with `N` constant virtual users (closed model).                                                                                     |
| `--duration 30s`  | How long to run. With `--rate` or `--vus`, the length of that constant load. On its own, the file's stages are stretched or squeezed to fit, keeping their shape. |
| `--repeat N`      | Run the test `N` times, one after the other, saved as one group that [`mantix compare`](#mantix-compare) treats as one side. Not with `--json`.                   |
| `--json out.json` | Also write the full summary as JSON to this file.                                                                                                                 |
| `--quiet`         | Don't print the per-second lines; print only the final summary.                                                                                                   |
| `--base-url URL`  | Send requests to this address instead of each scenario's `baseUrl`, e.g. a staging server. The test file is not changed.                                          |
| `--label "text"`  | A note saved with the run, e.g. `"v2.3 on staging"`, to tell runs apart in the [run history](#run-context).                                                       |
| `--no-history`    | Don't save this run to the [run history](#run-history).                                                                                                           |
| `--history-file`  | Where the run history lives. Default `.mantix/history.db`.                                                                                                        |

Durations are written like `500ms`, `30s`, `2m`, `1h`, or a plain number of
seconds. Without `--duration`, `--rate` and `--vus` run for the file's
planned duration.

### Output

The first line names the test, its planned length and, inside a git
repository, the branch and commit it ran at (with `(dirty)` if tracked files
had uncommitted changes) and the label:

```txt frame="terminal"
  mantix · checkout · 30 s planned · main @ a1b2c3d (dirty) · v2.3 on staging
```

While the run goes, one line per second: elapsed time, iterations started
against the target, the p99 latency for that second, and the share of failed
requests.

```txt frame="terminal"
  12s  1,000/s (target 1,000)  p99 23.4 ms  err 0.4%
```

At the end, a table with one row per endpoint and a total, then each
threshold with its measured value, then a one-line verdict:

```txt frame="terminal"
endpoint              req     req/s   p50      p95      p99      max      errors
GET /products/:sku    1,500   50.0    3.9 ms   8.7 ms   12.1 ms  31.0 ms  0.0%

✓ p99 < 250ms     12.1 ms
✓ errors < 1%     0.0%

✓ PASSED: all thresholds met
```

Latencies are corrected for coordinated omission (see [Reading results
honestly](/mantix/concepts/results/)).

### Exit codes

| Code | Meaning                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------- |
| `0`  | The run finished and every threshold passed (or there were none).                               |
| `99` | At least one threshold failed. The same code as k6.                                             |
| `1`  | An error: the file could not be loaded, an option or threshold was invalid, or the run crashed. |

In a CI step, that is all you need:

```yaml
- run: npx mantix run checkout.ts --json results.json
```

### JSON summary

`--json` writes the run's summary as one JSON object:

| Field        | Contents                                                                                                                                                                                                         |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`    | Format version, currently `1`.                                                                                                                                                                                   |
| `run`        | The run: `id`, `testName`, `status` (`finished`, `stopped`, `aborted` or `crashed`), start and end times, the plan, `thresholds` with each one's `actual` value and `passed`, and its [`context`](#run-context). |
| `seconds`    | How many seconds of data the summary covers.                                                                                                                                                                     |
| `iterations` | Counts: `started`, `completed`, `failed`, `dropped`.                                                                                                                                                             |
| `total`      | Statistics for all endpoints together.                                                                                                                                                                           |
| `endpoints`  | The same statistics, one entry per endpoint.                                                                                                                                                                     |

Each statistics block (`total` and every entry of `endpoints`) has
`endpoint`, `requests`, `errors`, `errorRate` (0 to 1), `rps`,
`errorsByKind`, the corrected `latency` and the `uncorrected` latency next
to it. Latencies are `p50`, `p90`, `p95`, `p99` and `max`, in
milliseconds. The
format is pre-release and may change; the `version` field will tell you when
it does.

## mantix compare

Compares a run with a baseline from the run history and says, for every
endpoint, whether it got slower, faster, stayed the same, or whether the
difference is too noisy to tell. [Comparing runs](/mantix/guides/comparing-runs/)
explains the verdicts.

```sh
mantix compare [run] [--baseline run] [--baseline-runs N] [--band 5] [--fail-on-regression p95:+10%] [--json out.json]
```

| Flag                       | What it does                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[run]`                    | The run to judge. Default: the newest run. A run id (or its start), `label:<text>`, `branch:<name>` or `commit:<sha>`, which take the newest match.     |
| `--baseline run`           | What to compare against, picked the same way, always a run of the same test. Default: the run before.                                                   |
| `--baseline-runs N`        | Use the `N` newest matching runs as the baseline, e.g. `--baseline branch:main --baseline-runs 5`.                                                      |
| `--band 5`                 | Latency changes smaller than this percent count as the same. Default 5.                                                                                 |
| `--fail-on-regression ...` | Exit with code 99 when an endpoint is confidently worse than a limit: `p50`, `p95` or `p99` in percent, `errors` in percentage points, comma separated. |
| `--json out.json`          | Also write the comparison as JSON: the run ids of each side, warnings, every metric of every endpoint with its range and verdict, and the regressions.  |
| `--history-file`           | Where the run history lives. Default `.mantix/history.db`.                                                                                              |

A run from a `--repeat` brings its whole group with it, on either side.
The exit code is `0` when nothing broke a limit, `99` when something did,
and `1` for an error, such as no run matching a selector.

## mantix ui

Starts the local dashboard for a test file.

```sh
mantix ui <file> [--port 4100] [--label "text"]
```

| Flag             | What it does                                               |
| ---------------- | ---------------------------------------------------------- |
| `<file>`         | The test file, as for `mantix run`.                        |
| `--port 4100`    | The port for the dashboard. Default `4100`.                |
| `--base-url URL` | As for `mantix run`: every run hits this address.          |
| `--label "text"` | A note saved with every run started from this dashboard.   |
| `--no-history`   | Keep runs in memory only; nothing is saved.                |
| `--history-file` | Where the run history lives. Default `.mantix/history.db`. |

Open [http://localhost:4100](http://localhost:4100), press **Start** to begin
the run and **Stop** to end it. The dashboard shows a latency heatmap with
p50 and p99, target against achieved throughput, errors by kind, and an
endpoints table you can click to expand. See [Reading the
dashboard](/mantix/start/dashboard/).

The server only listens on your machine. Stop it with <kbd>Ctrl</kbd>+<kbd>C</kbd>.

## Environment variables

Some flags can also be set with environment variables, which is handy in CI
or a container. A flag on the command line always wins.

| Variable                                  | Same as                              |
| ----------------------------------------- | ------------------------------------ |
| `MANTIX_BASE_URL=https://staging.example` | `--base-url https://staging.example` |
| `MANTIX_PORT=4200`                        | `--port 4200` (`ui` and `dev`)       |
| `MANTIX_HISTORY_FILE=runs.db`             | `--history-file runs.db`             |
| `MANTIX_HISTORY=false`                    | `--no-history`                       |
| `MANTIX_LABEL="v2.3"`                     | `--label "v2.3"`                     |

## Run history

Every run, from `mantix run`, `mantix ui` or `mantix dev`, is saved to a
SQLite file, `.mantix/history.db` in the folder you run Mantix from.
Restart `mantix ui` and earlier runs of the same test file are still there.
Add `.mantix/` to your `.gitignore`.

The history flags can also be set with [environment variables](#environment-variables).

The file keeps the raw data of each second (latency histograms, status
codes, error counts), never precomputed percentiles, so any window of any
run can be summarised exactly later and runs can be compared fairly.

If Mantix is stopped mid-run (<kbd>Ctrl</kbd>+<kbd>C</kbd>), the run is saved
as **stopped**. If the process is killed outright, the run is marked
**crashed** the next time the history is opened, with every second saved up
to that point. Saving never stops a test: if the file can't be written,
Mantix prints a warning and carries on.

### Run context

Each run also records where it came from, so runs can be told apart and
compared later, even across projects that share one history file
(`--history-file`):

| Field           | What it holds                                                                                                                                                                                        |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `project`       | The `name` in the nearest `package.json`, looking from the folder you run Mantix in up to the root of its git repository. Without one, the repository's folder name, else the current folder's name. |
| `git`           | `commit` (the full SHA), `branch` (absent on a detached HEAD) and `dirty` (tracked files had uncommitted changes; untracked files don't count). Absent outside a git repository or without git.      |
| `mantixVersion` | The version of Mantix that ran the test.                                                                                                                                                             |
| `machine`       | `hostname`, `os` (e.g. `linux x64`) and the `node` version.                                                                                                                                          |
| `label`         | The text from `--label` or `MANTIX_LABEL`, if any.                                                                                                                                                   |

Git is asked once when each run starts, with a short timeout; if it is
missing or slow, the run goes ahead without the `git` field. With
`mantix ui` and `mantix dev`, the label from the command line applies to
every run started from that dashboard.

### HTTP API

The dashboard reads the history through the local HTTP API. Every run it
returns includes its `context`.

| Endpoint                    | Returns                                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/runs?limit=50`    | Runs of the loaded test file, newest first. Add `project=`, `branch=` or `label=` to keep only matching runs, e.g. `?branch=main&label=nightly`. |
| `GET /api/runs/:id`         | One run.                                                                                                                                         |
| `GET /api/runs/:id/seconds` | Every second of a run, histograms included.                                                                                                      |
| `GET /api/runs/:id/events`  | The live stream; for a saved run, a replay that then ends.                                                                                       |

## mantix dev

Everything `mantix ui` does, plus a watcher that lets you test your test
while you write it.

```sh
mantix dev <file> [--port 4100] [--label "text"]
```

It takes the same `--port`, `--base-url`, `--label` and history flags as `mantix ui`.

When it starts, and then every time you save the test file or any file in
its folder, Mantix reloads the test, runs each scenario's `setup`, **one**
iteration and `teardown`, and prints that iteration as a small waterfall:

```text
  ↻ examples/checkout.ts · checkout · 4 requests in 183 ms ✓
    GET /products/:sku  200     41 ms  ▕███████                         ▏
    POST /cart/items    200     50 ms  ▕       █████████                ▏
    GET /cart/:id       200     33 ms  ▕                ██████          ▏
    POST /checkout      200     57 ms  ▕                      ██████████▏
```

Errors follow in plain words, such as a schema mismatch with the value
that arrived, or a script error with the line of your file that threw. If
the file does not load (a syntax error, say), Mantix says why and keeps the
last version that worked. A run you start from the dashboard always uses
the latest version.

Files you import from the same folder are reloaded too. Packages in
`node_modules` are not, so restart `mantix dev` after installing or
updating one.

## The demo target

Not part of the CLI, but you will use it with every example in these docs:

```sh
pnpm --filter @mantix/demo-target start
```

It serves `GET /products/:sku`, `GET /cart/:id`, `POST /cart/items` and
`POST /checkout` on [http://localhost:4200](http://localhost:4200) (or
`$PORT`), with planted bugs: a 1.5 second stall every 30 seconds, about 2%
`503`s on checkout, and about 1% schema drift on the cart. See the [quick
start](/mantix/start/quick-start/#2-start-the-demo-target).
