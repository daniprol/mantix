---
title: Reading the dashboard
description: What each part of the live dashboard shows, and what to look for while a run is going.
---

`mantix ui <file>` starts a local server and the dashboard at
[http://localhost:4100](http://localhost:4100). Nothing leaves your machine.

```sh
npx mantix ui checkout.ts
```

Press **Start run** to begin and **Stop** to end it early. The run uses the
load model, thresholds and scenarios from your file, exactly as
`mantix run` would. Every page has its own URL, so the browser's back
button, reloads and shared links all work.

## The sections

The sidebar has four:

- **New run**: your test, its checks and the planned load. Change the rate
  or duration before you start.
- **Live**: the run going on right now. Grayed out when nothing is running.
- **Runs**: every run in the history, newest first.
- **Compare**: two runs side by side.

At the bottom of the sidebar, the theme switch picks System, Light or
Dark. System follows your operating system, and the choice is remembered.

## A run

The bar at the top names the test and the run (when it started, the git
branch and commit), its state, and the actions: **Stop** while it runs,
**Run again** and **Compare** once it ends.

Below it, three numbers: throughput, **p95** latency and the error rate.
p95 means 95 in 100 requests were faster than this. Under them, your checks
with their measured values, red when they fail.

### The timeline

Three charts share one time axis, one column per second:

- **Load**: the planned rate, dotted, and the requests that actually went
  out. When they fall below the plan, the server could not keep up.
- **Latency**: a heatmap of every request, darker where more of them
  landed, with the **p50** and **p95** lines on top. The scale is
  logarithmic, so 5 ms and 5 s both fit. A latency check draws its limit.
- **Errors**: failed requests per second, in red.

Drag across the charts to select a range. Everything below then describes
only those seconds. The **Span** buttons switch between **Now** (the last
30 seconds of a live run), **Whole run** and your range.

What to look for: a band that drifts upwards (the server slows down as it
fills up), a second band above the first (some requests take a slower
path), and vertical stripes (a stall).

The latencies are corrected for coordinated omission: measured from when
each iteration should have started. The [results
page](/mantix/concepts/results/) explains why.

### Endpoints

One row per endpoint, named by its route template (`GET /cart/:id`), not by
each concrete URL, slowest first. Each row shows its p95 over time on the
same time axis as the charts, with its own scale, then p50, p95 and the
error share for the selected span.

Click an endpoint to open the same view for it alone, with its percentiles
(p50 to max), its status codes and its failures grouped by cause. The back
arrow and the breadcrumb return to the run.

## Comparing two runs

**Compare** on a finished run opens it against the run before it. The
Compare section lets you pick any two.

The baseline is drawn in gray under the current run: its load line, its
p95 line, and its errors as bars hanging below the axis, mirroring this
run's errors above it. The endpoint list shows the baseline p95, this
run's p95 and a verdict on the change: "12% slower", "same", "unclear" or
"too few", with the range the change most likely lies in under it.
Slowdowns come first, and each curve overlays both runs. A fourth figure
counts the endpoints by verdict. An endpoint opens the same comparison for
that endpoint alone, with verdicts for its p50, p95 and p99.

[Comparing runs](/mantix/guides/comparing-runs/) explains the verdicts and
how they are worked out.

## Checks

Your thresholds are checked while the run is going, so you see a failure
the moment it happens. A threshold with `abortOnFail: true` stops the run
there and then, once its grace period (5 s by default) is over.
